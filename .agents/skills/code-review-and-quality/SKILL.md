# Code Review & Quality (mtest)

The product is **truthful exit codes and an honest report** — so a review here
checks two things a generic reviewer misses: that a *crash is never laundered
into a failure through any layer*, and that *every committed transcript is
traceable and its normalizer is minimal*. The output is a structured Markdown
report — findings grouped by severity, each with a `file:line` reference and a
quoted snippet, then a clear verdict.

Project rules live in [AGENTS.md](../../../AGENTS.md) and override this skill;
its standing per-phase quality gate (dual adversarial external review at plan
and diff checkpoints) is the doctrine this single-reviewer pass prepares for —
the findings you surface are what the two external reviewers confirm or
escalate. Companion skills own the production rules; when a finding is "this
violates rule X", **cite the owner, don't restate it**:

- [mojo-coding-guidance](../mojo-coding-guidance/SKILL.md) — exit-code
  fidelity, supervision invariants, the two FFI boundaries, named errors, the
  rent test (unnecessary constructs are findings, not nits — severity per the
  table below).
- [mtest-testing-patterns](../mtest-testing-patterns/SKILL.md) —
  failing-test-first, the oracle patterns, exact equality.
- AGENTS.md — layering, commit grammar and scopes, transcript lifecycle,
  Ask-first boundaries; the global `mojo-syntax` skill is the authority on
  current syntax.

Before reading a line: run the smallest focused gates that cover the diff (a
red gate is finding #1 — name *which* stage went red); read the diff with its
commit messages; check whether the change touched a frozen zone (protocol
snapshots, fixtures, a pin, the transcript format, the CLI contract) — those
are Ask-first boundaries, and a regenerated transcript must name the
oracle-side reason in the commit body.

## Axis 1: Transcript fidelity & provenance (this repo's signature axis)

- **Is every committed transcript traceable to a fixture, a scenario, and a
  pinned toolchain?** Each snapshot header names the generator, the resolved
  mojo version + commit, the os/arch, the normalizer version, the fixture, and
  the scenario. A transcript that cannot be traced does not get committed —
  full stop. A header claiming a version the toolchain isn't pinned to is
  **Critical**.
- **Is the normalizer ANCHORED and MINIMAL?** The timing-token rewrite fires
  only on report-grammar lines at or after the LAST `Running <N> tests for`
  anchor; a report-lookalike a fixture *printed* must stay byte-exact.
  **Over-normalization is as serious as nondeterminism** — a normalizer that
  scrubs a byte it didn't have to has erased evidence the parser needs. The
  only sanctioned rewrites: repo-root prefix → `<REPO>`, timing tokens →
  `[ T ]` within the report block, stack dump → `<STACK-DUMP>`. A new rewrite
  is a deliberate, reviewed extension, never a quiet addition.
- **`transcripts-check` regenerates and diffs — it does not trust a hash.** A
  change making it compare a hash, a size, or a sample instead of regenerating
  and byte-diffing everything is **Critical** — it silently weakens the
  strongest gate in the repo.
- **Are the generator's self-asserts hard failures, on every scenario?** A
  disagreement belongs at generation time, not as a baffling Mojo failure
  later.
- **No absolute path in any snapshot.** An absolute path, a
  `llvm-symbolizer` line, or a raw `Stack dump` header surviving into a
  committed transcript is a **Critical** provenance break.
- **Any hand edit to a generated artifact?** Transcripts and MANIFEST are
  regenerated by the script only; a hand-edited byte is **Critical** — it
  breaks the provenance argument the whole repo stands on. A new script or CI
  step that downloads anything breaks hermeticity: **High** regardless of
  justification.

## Axis 2: Exit-code honesty (the product)

- **Is crash ≠ fail preserved through EVERY layer?** A signal-terminated child
  surfaces as CRASH, an assertion failure as FAIL, from the `waitpid` decode
  in `exec` through the verdict map in `session` to the summary and the
  process exit code. A `Signaled(signo)` collapsed into `Exited(1)` anywhere
  is **Critical** — the exact lie the tool exists to prevent.
- **Structured termination is NEVER 128+N.** The raw status is decoded
  structurally; a signal surfacing as exit `128 + signo` anywhere is **High**.
  That encoding is the shell's; the runner must not adopt it.
- **Is a deadline kill attributable to the runner, not the test?** The
  runner's own SIGTERM/SIGKILL must produce a distinct `TimedOut`, never a
  `Signaled` CRASH. Collapsing the two is **High**.
- **Does the exit-code precedence match the contract, exactly?** Usage error >
  internal error > test failure > empty walk > success. A swapped rank in that
  pure function is **High** — it's what a CI system trusts.
- **No `mojo run` anywhere.** In the runner, a script, or a doc example — it
  masks crash exit codes to 1. Any occurrence in a path that reads an exit
  code is **Critical**.

## Reviewing AI-generated code

False confidence is the dominant failure mode. Generated Mojo tends to: emit
last-year's syntax (`mojo-syntax` is the authority, not memory — check
explicitly, including ```mojo blocks inside docs); reach for `mojo run`;
collapse a signal into exit 1; decode `waitpid` as 128+N; scan a report from
the first `Running` line instead of the last; over-normalize a transcript to
make a diff green; allocate in the child between fork and exec; kill only the
child and deadlock on a grandchild; add tests that mirror the implementation
instead of the oracle; wrap one comparison in a trait + factory + config
struct "for extensibility" (generated code over-abstracts by default, and the
ceremony arrives fully documented, which makes it look deliberate); and write
commit messages with an AI trailer this repo forbids. Check each explicitly —
polish is not correctness.

## Severity and output

| Severity | Meaning |
|---|---|
| **Critical** | crash laundered into a fail, `mojo run` in an exit-code path, hand-edited transcript, absolute path in a snapshot, Python under `src/`, allocation in the child before exec, red gate merged, `transcripts-check` weakened to a hash |
| **High** | 128+N termination, deadline kill collapsed into a crash, wrong exit-code precedence, un-anchored parse, over- or under-normalized transcript, missing group-kill or pipe drain, up-graph import, a foreign call outside the two audited boundaries (`platform`, `native/` via `exec`), obsolete syntax that will break, a speculative plug-in layer with nothing plugged |
| **Medium** | missing test for new behavior, vague/unlocated error message, unpinned magic constant, missing provenance comment, unmeasured perf claim, an unnecessary construct failing the rent test, dead or duplicate code |
| **Low** | naming, a redundant copy, a docstring gap |
| **Nit** | subjective; label it as such |

End with a **verdict**: *approve*, *approve with nits*, or *request changes*,
and the one or two findings that gate the merge. Prefer few high-confidence
findings over a long list; a review the author trusts is one they act on.
